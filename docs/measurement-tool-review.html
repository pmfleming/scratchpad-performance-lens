1 · Executive summary

Since the prior review, the repository has done the cheap, high-leverage half of the roadmap (steps 1–2 plus parts of 3) and the single most valuable correctness fix. The 2,648-line producer monolith is now a clean producers/ module, the brittle git-LOC parser has been replaced with a real lexer, and the highest-risk scoring kernels now have unit tests. All 13 tests pass.

What remains undone is the pivot the prior review hinged on: typed artifacts and a generated schema (I-1). The dashboard contract is still an informal collection of serde_json::Value blobs read by string key. That is a maintainability gap — but the more pressing finding from this pass is on the second question: several paths let the tool present a healthy seven-promise board from data that does not justify it. "Covered" currently means measured, not passing; one of the two synthetic fallbacks is not flagged as synthetic; and the check that the workload actually reached the promised scale is stubbed out.

3 · Part 2 — Measurement accuracy vs the promises

The tool tracks a set of headline promises (in review.rs as target_promises): GB-class text files, 10,000+ files, 10,000+ tabs, 1,000+ views/splits, sub-100 ms visible response, and fast first-search response + completion. The findings below are ordered by how badly they let the board overstate promise health.

CRITICAL can present unjustified promise health HIGH measurement fidelity MEDIUM drift / consistency

CRITICAL "Covered" means measured, not passing A-1

Where: build_review_scenario in src/producers/review.rs.

coverage_status (covered / thin / missing) is derived purely from !rows.is_empty() via coverage_axis — i.e. whether an artifact row exists. A scenario reads as "covered" even if every benchmark is over budget and every ceiling is breached. budget_misses and ceilings_reached are computed, but they sit beside the headline status rather than feeding it. On a coverage matrix, "covered" will be read as "promise met."

Recommendation: Add a distinct promise_health: pass | at_risk | fail | unmeasured axis that is computed from budget misses, ceilings reached, and input provenance — kept separate from coverage: measured | thin | missing. The matrix should lead with health, not coverage.

CRITICAL Resources fallback is not flagged synthetic A-2

Where: summarize_resources in src/producers/resources.rs.

The fallback branch sets only fallback_reason; unlike the capacity producer it never sets synthetic: true. When the resource_probe binary fails to build, ~210 lines of fabricated allocation / working-set / session-cost numbers flow downstream with no machine-readable synthetic marker for the dashboard to gate on — and (per A-1) they then appear as fully "covered" scenarios in the performance review. This is a one-line inconsistency with real consequences.

Recommendation: Mirror capacity exactly — set meta.synthetic and summary.synthetic in the fallback branch. Add a test asserting it, as capacity already has.

CRITICAL Capacity fallback fabricates an all-green ceiling A-3

Where: fallback_capacity_events in src/producers/capacity.rs.

The synthetic formula elapsed_ns = value.min(10_000) * 1_000 caps elapsed time at 10 ms, far below every 120–180 ms threshold. So ceiling_reached is false for every promise in fallback — a failed probe build yields "all scale promises pass." It is tagged synthetic: true now (good), but nothing forces that flag to override the green status, and a fabricated pass is exactly what the prior review (I-4) warned against.

Recommendation: Emit ceiling_reached: null / failure_mode: "unmeasured" for synthetic capacity rows instead of a fabricated pass, and let A-1's promise_health resolve to unmeasured whenever synthetic is set.

HIGH Nothing asserts the sweep reached the promised scale A-4

Where: review.rs — scale_checks is hardcoded [].

scale_checks is an empty literal, so missing_scale_targets always sums to 0, and implementations / implementation_count are always empty/0. The promises are magnitudes ("10,000+ tabs", "GB-class"), yet the natural check — did the workload sweep actually reach the promised number? — is stubbed out. For example file_size_ceiling tops out at exactly 1 GB; passing at the boundary is not the same as headroom above it, and nothing records that distinction.

Recommendation: Carry a promised_scale on each scenario in the registry and have scale_checks assert max_workload_value >= promised_scale, marking a gap when a sweep stops short of the promise.

HIGH Budget compliance is mean-based, but the promise is tail-based A-5

Where: over_threshold, slowspot_signals, search_signals; row construction in slowspots.rs / search.rs.

"Sub-100 ms visible response" is a tail property, yet the budget checks compare mean_ns to the threshold. Only frame-metrics checks p95/p99. Worse, max_ns/min_ns are fabricated as mean ± 2·std_dev — a Gaussian approximation presented under field names that imply observed extremes. A tail-driven regression with a healthy mean passes silently.

Recommendation: Gate responsiveness promises on a percentile, and either read Criterion's real min/max or rename the derived fields (e.g. approx_p95_ns) so they are not mistaken for measured extremes.

MEDIUM Promise list and scenario list have drifted A-6

Where: target_promises vs review_scenarios() in review.rs.

The prose says "seven promises"; target_promises lists six strings; review_scenarios() defines seven scenarios — and they do not map 1:1 (no promise string for Large Text Mutation or Session Persistence Restore; "sub-100 ms visible response" has no scenario id). This is the I-3 drift trap surfacing at the promise layer itself.

Recommendation: A single Promise → Scenario registry, with the promise string carried on the scenario, so the count and the mapping become a compile-time fact rather than two hand-kept lists.

MEDIUM Stale-budget risk from duplicated benchmark metadata A-7

Where: BUILTIN_METADATA (~470 lines) + load_benchmark_metadata in shared.rs.

The Rust table still hand-mirrors Scratchpad's bench budgets. load_benchmark_metadata lets the repo JSON override a key when present, so live benches win where they exist — but any benchmark not in the repo JSON is judged against a Rust-side budget that can silently drift from what Scratchpad actually ships, and report "within budget" against a stale number. (This is the prior review's I-7, still open.)

Recommendation: Treat the Scratchpad-shipped JSON as authoritative; keep only minimal defaults in Rust, or generate the builtin table from that JSON at build time.
