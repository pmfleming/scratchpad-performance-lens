1 · Executive summary

scratchpad-performance-lens is a focused, well-scoped Rust CLI that runs benchmarks and probes against a configured Scratchpad editor checkout and emits JSON artifacts for a dashboard owned by a sibling repo. The boundary between this lens (producer logic), the dashboard (project-management-board), and the app under test (scratchpad) is clearly documented and genuinely respected — that discipline is the project's strongest asset.

The codebase is healthy in intent but structurally lopsided: nearly all logic for nine different producers lives in a single 2,648-line file, and the entire data pipeline is built on untyped serde_json::Value blobs accessed by string keys. Both choices work today but cap maintainability and — more importantly for the second half of this review — block reuse. The same project already has a sibling (rust-quality-lens) and an explicit ambition to share infrastructure; roughly half of the current code is project-agnostic engine that could power both lenses if it were typed and extracted.

Headline recommendation: introduce typed artifact structs (serde) as the contract, then carve a lens-core crate out of the generic engine (config, artifact IO, Criterion ingestion, stat primitives, probe runner, flamegraph engine, git LOC metrics). Leave this repo as a thin layer of Scratchpad-specific taxonomy and probes. That single move pays down most of the maintainability debt and unlocks reuse across rust-quality-lens and any future lens.

2 · What the tool is

A Rust binary (exposed as both splens and scratchpad-performance-lens) with three commands:

  • catalog — emits a JSON task manifest describing the producers and their output artifacts.
  • telemetry — inspects the live Scratchpad session directory and emits a session/app-package payload.
  • measure <tool|all> — runs one or all of nine producers, each writing a JSON artifact into the configured output_dir.

The nine measure producers:

ProducerArtifactWhat it does
slowspotsslowspots.jsonRuns Criterion benches, ranks latency hotspots with stability/score signals.
frame-metricsframe_metrics.jsonBuilds and runs a release probe binary; captures frame p95/p99 vs budget.
searchsearch_speed.jsonFocused search-benchmark view with throughput and scaling axes.
capacitycapacity_report.jsonCeiling sweeps; finds first "unusable" workload per promise.
resourcesresource_profiles.jsonAllocation / working-set / session-cost scenarios.
flamegraphsflamegraphs.jsonDrives cargo flamegraph and indexes resulting SVGs.

performance-reviewperformance_review.jsonScenario-first coverage matrix against the "seven promises."

Configuration is a three-field TOML (project_name, project_root, output_dir). Two producers (capacity, resources) fall back to large synthesized datasets when their probe binaries fail to build or run, marking the output probe_status: "fallback_completed".

4 · What works well

Clear ownership boundary

The README and extraction notes carve an unambiguous line: this repo owns producers, project-management-board owns the dashboard, scratchpad owns probes/benches. Boundaries this explicit are rare and valuable.

Honest fallback signalling

Synthetic fallbacks are tagged (probe_status: fallback_completed, per-row note: "measurement-layer fallback workload", fallback_reason). The intent to not silently pass off fabricated numbers is good.

Thoughtful measurement model

The separation of ceiling/promise-health vs targeted-path vs diagnostic-profile probe classes is a genuinely good conceptual frame, and the "seven promises" scenario matrix gives the data a narrative spine.

Defensive IO

Helpers like read_json, load_json_file, and load_ndjson_file degrade gracefully and accumulate warnings rather than crashing — appropriate for a tool pointed at messy live state.

Small, correct config surface

LensConfig is minimal and sensible: relative output_dir resolves under project_root, project name defaults from the directory.

Pure, testable kernels exist

Much of the scoring/classification logic is already written as pure functions (latency_score, stability_label, infer_limiting_resource, classify_path). They are shaped for testing even if not yet tested.

The two NDJSON edge-case tests

The only unit tests present (concatenated objects, trailing garbage) target exactly the kind of real-world malformed input that bites parsers. Good instinct — just under-applied.

5 · Improvement opportunities

CRITICAL structural / blocks reuse HIGH correctness or maintainability risk MEDIUM worthwhile cleanup LOW polish

CRITICAL Untyped serde_json::Value is the whole pipeline I-1

Where: producers.rs and shared.rs, pervasive.

Every artifact is assembled with json!({...}) and later read back with chains like row.get("mean_ns").and_then(Value::as_f64).unwrap_or(0.0). This pattern appears hundreds of times. The dashboard JSON shape is effectively a public API, yet it is defined only implicitly and enforced nowhere. Consequences:

  • A mistyped key ("mean_n") silently yields a default — no compile error, no panic, just wrong data.
  • Producers and their render_* functions independently "know" the same shape; the report producers (speed-report, performance-review) re-parse upstream artifacts by string key, so a field rename must be chased across files by hand.
  • No reusable engine can be built on top of ad-hoc Value shapes — typing is the prerequisite for everything in §6.

Recommendation: Define #[derive(Serialize, Deserialize)] structs per artifact (Slowspot, SearchRow, CapacityScenario, ReviewScenario, …). Build and read those, serialize at the edge. Optionally derive JSON Schema and hand it to the TypeScript dashboard so the cross-language contract is generated, not transcribed.

CRITICAL A 2,648-line producer monolith I-2

Where: src/producers.rs.

Nine producers, all their CLI renderers, the git LOC-metrics engine, the capacity/resource fallback datasets, the review-scenario model, and dozens of private helpers share one file. Navigation is hard, ownership is unclear, and unrelated changes collide. Notably, the predecessor Python layout had one module per tool (tools/capacity_report.py, tools/frame_metrics.py, …) — the Rust port collapsed that structure rather than preserving it.

Recommendation: Split into a producers/ module — one file per producer plus a small shared render and fallback module. This is mechanical and low-risk, and it is the natural seam along which the reusable engine (§6) later separates.

HIGH The scenario taxonomy is restated in 4+ places I-3

Where: BUILTIN_METADATA, FLAMEGRAPH_CONFIGS (shared.rs); capacity_config, fallback_capacity_events, fallback_resource_events, review_scenarios, measurement_gap_scenarios, and inline editor_families/tab lists (producers.rs).

The same scenario identifiers and workload families ("tab_count_ceiling", "search", "file-load", …) are independently hand-written across many tables. A capacity scenario, its threshold, its profile mapping, its fallback values, and its membership in a review scenario all live in separate literals that must be kept in lockstep manually. This is a classic drift trap — adding or renaming one scenario means editing five tables and hoping none were missed.

Recommendation: One source-of-truth registry: a typed Scenario table that carries id, family, threshold, profile ids, gap description, and fallback shape. Every producer reads from it. Drift becomes a compile error rather than a silent mismatch.

HIGH Large hand-written synthetic datasets can be mistaken for real data I-4

Where: fallback_capacity_events (~95 lines), fallback_resource_events (~210 lines).

When a probe fails to build, these produce dozens of fabricated-but-plausible measurements with formulas like elapsed_ns = value.min(50_000) * 1_000 and allocated = value * 1536. The tagging (I-credit it in §4) is good, but the volume of fabricated data is high and its shape is identical to real output. On a dashboard, a green "fallback_completed" run can read as a successful measurement.

Recommendation: Keep fallbacks but (a) derive their scenario list from the single registry in I-3 rather than re-listing it, (b) make the synthetic provenance impossible to miss downstream (e.g. a top-level synthetic: true the dashboard must surface), and consider whether an empty/"unmeasured" state is more honest than fabricated numbers for some panels.

HIGH rust_test_line_mask is a brittle hand-rolled parser I-5

Where: producers.rs (project-code metrics).

Test-vs-application line classification works by counting raw {/} characters to track #[cfg(test)] scope. Braces inside string literals, char literals, or comments will desynchronize the stack and miscount lines. It is also completely untested despite being pure and deterministic — an ideal unit-test target.

Recommendation: At minimum, add table-driven unit tests (nested modules, braces in strings, cfg_attr). Better: when this graduates into the shared engine (§6E), back it with a real lexer pass (e.g. token-aware brace counting) so the metric is trustworthy across projects.

MEDIUM Policy magic-numbers are scattered as inline literals I-6

Where: stability thresholds 0.1/0.2, score formulas, family_priority weights, capacity_config thresholds, fallback multipliers (1.25, 4096, 1536, /3, /2).

These literals encode Scratchpad's performance policy (what counts as "unstable," how families are prioritized) but are buried mid-expression with no names or rationale. They are exactly the values a reviewer or future maintainer will want to tune.

Recommendation: Promote to named consts grouped in one policy module, each with a one-line comment on its meaning. When the engine is extracted, these constants become the per-project configuration surface.

MEDIUM Builtin benchmark metadata duplicates the Scratchpad repo's own tables I-7

Where: BUILTIN_METADATA — ~470 lines of static benchmark descriptors in shared.rs.

This table mirrors data that also lives in Scratchpad's benches/benchmark_targets.json / search_benchmark_targets.json (which load_benchmark_metadata already merges in). Maintaining a second copy in Rust risks the lens and the benches drifting apart — the lens could describe a benchmark that no longer exists, or miss one that does.

Recommendation: Treat the Scratchpad-shipped JSON as authoritative and keep only minimal defaults in Rust, or generate the builtin table from that JSON at build time. The lens should follow the benches, not re-declare them.

MEDIUM Almost no tests on the logic that matters I-8

Where: only app_package NDJSON parsing + a thin CLI contract test are covered.

The scoring, classification, ranking, and triage functions — the actual judgment the tool encodes — are pure and untested: latency_score, stability_label, infer_limiting_resource, family_priority, over_threshold, throughput_mb_s, classify_path, rust_test_line_mask. A refactor (especially the typed-struct migration in I-1) has no safety net.

Recommendation: Add focused unit tests for these kernels before refactoring. They double as executable documentation of the scoring policy.

MEDIUM Rendering is coupled to producers and re-parses its own output I-9

Where: the nine render_* functions in producers.rs.

Each producer builds a Value, then a render_* function reads that same Value back by string key to print a CLI summary — a second, parallel place that hard-codes the schema. With typed artifacts (I-1) this collapses into an impl Display (or a small Render trait) on the struct, eliminating the re-parse and the duplicate key knowledge.

LOW Smaller items I-10

  • Two byte-identical binaries. splens.rs and scratchpad-performance-lens.rs are the same 3 lines. Harmless (Cargo needs separate files for separate bin names), but a comment noting they are intentional aliases would prevent "fix the duplicate" churn.
  • absolutize_from swallows canonicalize errors via .unwrap_or(joined) — a non-existent project_root silently proceeds with an un-normalized path. A clear error would be friendlier.
  • Inconsistent failure policy across producers. Some bail! (frame-metrics), some fall back to synthetic data (capacity/resources), some skip silently. Documenting the intended contract per producer would help consumers reason about partial runs.
  • load_ndjson_file has a dead tail branch (if !parsed_any && line.trim().is_empty() after an early continue on empty lines) — minor, worth pruning during the split.

6 · Path to reusable components

The repo already lives in an ecosystem: it explicitly defines itself against a sibling rust-quality-lens and is consumed by project-management-board. The natural next step is a shared lens-core crate that both lenses depend on. The dividing principle is clean:

Extract the engine (how to measure, ingest, score, and write artifacts). Keep the policy (which Scratchpad scenarios exist, what their budgets are, the seven promises) here.

Going component by component, here is what is ready to graduate and what should stay:

Component (current location)VerdictWhy
6A · Lens skeleton
LensConfig, write_visibility, read_json, catalog, measure dispatch, run_command		 EXTRACT Nothing here is Scratchpad-specific. It is a generic "run producers against a project root, write JSON to output_dir, emit a catalog" framework — exactly what every lens needs.
6B · Criterion ingestion
criterion_estimate_paths, benchmark_name_from_estimate_path, benchmark_key, estimate readers		 EXTRACT Pure Criterion plumbing. Works for any Rust project with Criterion benches; zero domain knowledge.
6C · Stat / format primitives
variance_ratio, stability_label, latency_score, throughput_mb_s, ns_per_kb, human_bytes, safe_delta		 EXTRACT Generic performance math and formatting. The thresholds become parameters (see I-6); the formulas are universal.
6D · Probe runner
run_probe_object, run_probe_events (build a release bin, run it, parse JSON / NDJSON)		 EXTRACT A reusable "build-and-run a probe binary, collect JSON events" harness. Only the probe names are project-specific.
6E · Git code metrics
entire project-code producer: first-parent history, LOC counting, classify_path, rust_test_line_mask		 EXTRACT Completely project-agnostic — runs on any git + Rust repo. Almost certainly overlaps logic rust-quality-lens wants too; a prime candidate for the shared crate (fix I-5 in the process).
6F · Flamegraph engine
the cargo flamegraph driver + SVG indexing in flamegraphs()		 SPLIT The driving/indexing engine is generic; only FLAMEGRAPH_CONFIGS (the table) is Scratchpad policy. Separate engine from config.
6G · JSON/NDJSON loaders
load_json_file, load_ndjson_file (with warning accumulation)		 EXTRACT Generic robust loaders; the two existing tests move with them.
Benchmark metadata, flamegraph configs, capacity config, review scenarios, fallbacks KEEP This is the Scratchpad lens — the taxonomy, budgets, and seven promises. It stays here as the project's configuration of the shared engine.
app_package telemetry KEEP Parses Scratchpad's specific session manifest / temp-buffer layout. Domain-specific — stays. (Though the loaders inside it, 6G, are extractable.)

The enabling prerequisite is I-1 (typed artifacts). A shared engine cannot operate on ad-hoc Value shapes; it needs a small contract such as: 

// in lens-core
pub trait Producer {
    fn id(&self) -> &str;
    fn artifact_name(&self) -> &str;
    fn run(&self, ctx: &LensContext) -> anyhow::Result<Artifact>;
}

pub trait Render { fn render_cli(&self) -> String; }

// engine owns: config, catalog, dispatch, criterion ingestion,
// probe runner, flamegraph driver, git metrics, artifact IO.

// scratchpad-performance-lens owns: the Scenario registry, budgets,
// the seven-promise review model, app_package, and `impl Producer`
// for each Scratchpad producer.

8 · Sequenced roadmap

Ordered so each step de-risks the next. Steps 1–3 are valuable on their own even if the extraction in 4–6 is deferred.

#StepAddressesEffortPayoff
1Add unit tests for the pure scoring / classification / git-metric kernelsI-8, I-5SSafety net for everything below
2Split producers.rs into a producers/ module (one file per producer + render + fallback)I-2S–MNavigability; reveals the extraction seams
3Introduce a single typed Scenario registry; route producers + fallbacks through it; name the policy constantsI-3, I-4, I-6, I-7MKills the drift traps
4Replace json!/Value with #[derive(Serialize)] artifact structs; renderers become impl RenderI-1, I-9M–LType-safe contract; unblocks reuse
5Carve out lens-core (6A–6G) with Producer/Render traits; this repo depends on it§6LReuse across lenses
6Export JSON Schema (schemars) from the typed artifacts for the dashboardI-1SGenerated, versioned cross-language contract

If you only do one thing: steps 1 → 2 are nearly free and immediately make the code workable. If you want the reuse win: 3 → 4 → 5 is the spine, and step 4 (typing) is the pivot the rest hinges on.

9 · Appendix — file-by-file notes

src/producers.rs — 2,648 lines

The center of gravity. Holds all nine producers, their CLI renderers, the git LOC engine, the synthetic fallbacks, and the review-scenario model. Split target (I-2). Strong internal logic, but undertested (I-8) and built entirely on Value (I-1).

src/shared.rs — 778 lines

Mixes truly-generic engine helpers (Criterion ingestion, IO, stats — extractable, §6B/6C/6G) with ~470 lines of Scratchpad-specific static tables (BUILTIN_METADATA, FLAMEGRAPH_CONFIGS — keep, but see I-7). The clearest example of engine and policy entangled in one file.

src/app_package.rs — 322 lines

Telemetry for the live session directory. Domain-specific (stays), but its JSON/NDJSON loaders (6G) and the two tests are the extractable, reusable part. Well-defended against malformed input.

src/cli.rs — 213 lines

Clean clap definitions and dispatch. The catalog + measure scaffolding is generic engine (6A); the producer enum + run order is policy. Note the MEASURE_TOOLS / STANDARD_RUN_ORDER / MeasureSelection / MeasureTool set is a fourth place producers are enumerated — fold into the registry during step 3.

src/config.rs — 64 lines

Minimal and mostly solid. Only nit: silent canonicalize fallback (I-10). Generic — moves to lens-core (6A).

src/bin/*.rs & tests/cli.rs

Two identical entrypoints (intentional aliases, I-10). The CLI test verifies the catalog/telemetry contract and is appropriately tolerant when the Scratchpad checkout is absent — a good integration guard to keep as the engine moves.
